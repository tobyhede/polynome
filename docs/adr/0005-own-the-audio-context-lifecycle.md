# Own the audio context lifecycle in the engine

Polynome will treat the Web Audio context as an unreliable resource that may refuse to start, stall, or be taken away mid-run, and will make `metronome.js` solely responsible for detecting and recovering from that. iPhone Safari reports no error in any of these cases, so the engine cannot rely on exceptions to notice. The evidence is recorded in `docs/research/ios-safari-web-audio.md`. iOS is the only WebKit platform that requires user activation for Web Audio, so desktop testing never exercises these paths.

## Consequences

- The engine never awaits `resume()`. WebKit parks that promise and settles it neither way when the context is not allowed to start, so awaiting it deadlocks the start path and the look-ahead scheduler is never installed. Resume is requested, any rejection absorbed, and the scheduler installed regardless.
- Every context state other than `running` and `closed` is resumed, not only `suspended`. iOS uses `interrupted`, a WebKit state that predates its addition to the specification.
- The transport origin is anchored on the first scheduler tick at which the context is running, not when playback is requested. `currentTime` is frozen while a context is suspended or interrupted and never catches up, so an origin derived from it places every rhythm event in the past, where the lateness filter and the scheduler both discard it silently.
- An interruption does not re-anchor the transport origin. `currentTime` freezes with the interruption and resumes in phase, so the transport run stays correct; re-anchoring is what would replay past events.
- A `statechange` listener, registered once per context, re-requests resume whenever a transport run loses `running`. Scheduling stays parked until a tick observes `running` again. A refused `resume()` fires no `statechange` at all — WebKit's `resumeRendering` skips the state change on both the refusal and the failure paths — so the handler cannot re-enter itself and cannot run away.
- That same silence is why the handler is not the whole recovery. Its one request is also its last, and the gate it can be refused on is transient user activation, which the page may regain at any moment from a tap that has nothing to do with the metronome and which raises no event the engine can hear. So a run that has already anchored re-requests resume from the scheduler once a second for as long as it is not running, and the counter resets on any tick that sees `running` and in `stop()`. A run that has never anchored is left to the `audioerror` report instead: it tells the user to tap play again, and that tap is itself the activation a resume needs. The retry is deliberately throttled by tick count alone and not by a "resume already pending" flag, because WebKit parks the promise unsettled for exactly the refusals this retry exists to survive, so such a flag would latch on the first refusal and suppress every attempt after it.
- A rhythm event whose scheduled time has slipped behind the clock is pulled forward to the current time rather than dropped; one staler than the lateness limit is skipped deliberately. The limit is the tighter of 50 ms and a quarter of that rhythm layer's own step, so the quarter-step binds on any grid whose step is shorter than 200 ms and the 50 ms binds above it. The two bounds guard the same failure from opposite ends: a sound profile is only tens of milliseconds long, so drift beyond it puts the stop time before the start time, which produces no sound at all; and the pull comes out of the gap before that layer's next click, so a pull worth much of a step lands the two close enough to sound as a flam rather than a grid.
- `navigator.audioSession.type` is set to `playback` when playback starts and back to `auto` when it stops, scoped to the playing interval rather than held for the life of the page. Web Audio maps to the iOS `Ambient` session, which the hardware Ring/Silent switch and the lock screen both silence; `playback` lifts both and waives the background-interruption restriction as well. It is not free: `playback` maps to `AVAudioSessionCategoryPlayback`, for which WebKit never sets `MixWithOthers`, and Apple is explicit that activating a nonmixable session interrupts any other nonmixable session. For a metronome the audio most likely to be interrupted is the backing track its user is playing along to, and a page holding the override while stopped interrupts that track for a claim it is not using. Reverting is supported: `auto` maps to `AudioSessionCategory::None`, which clears the override and re-runs WebKit's heuristic back to `AmbientSound`. Whether the interrupted app actually resumes once the category reverts is unverified and needs hardware to establish. The type is Safari 16.4+, absent elsewhere, and silently ignored when a Permissions Policy withholds it, so every one of these calls is best effort and none of it can break starting or stopping.- The session type is claimed before the AudioContext is constructed on the first start. A context is created once and reused for the life of the page, so the session in force at construction is the one it is created under.
- A run whose context has never once reached `running` reports itself through `audioerror` about two seconds in — a tick count derived from the scheduler interval, not a second timer — and reports once per run. Until then such a run is the silent failure with no symptom: `playing` reports true, the scheduler ticks on, and nothing is ever heard. Reporting changes nothing else: the run stays playing and the scheduler stays installed, because the context may still be granted and a user returning from a call must still get their metronome. Both the counter and the reported flag reset in `stop()`, which `start()` runs over the previous run before beginning its own, so every run reports its own silence.
- That report is scoped to a run that never starts, and deliberately not to one that stops. The tick counter is reached only while the transport is still unanchored, so a run that anchors, sounds, and is then interrupted for good goes silent with a frozen playhead and says nothing. Known limitation, and the alternative is worse: an interruption is the ordinary case — every call, app switch and screen lock is one — so reporting each would put an error in front of the user on the path that most often recovers by itself, while the engine is still asking for the context back on both the `statechange` and the retry paths above. What it costs is that a permanent interruption looks, from outside, exactly like a metronome that is working and merely quiet. That is the same gap as the running-but-dead render thread below, and it wants the same answer: a positive indication that audio is advancing, not a second error.
- `MetronomeEngine` accepts an optional context factory so the lifecycle above is testable, and creates nodes through the context's factory methods rather than global constructors. The audio graph and all timing behaviour are unchanged.
- Engine lifecycle and scheduler tests live in `test/metronome-audio.test.js`, apart from the consequence-routing tests already in `test/metronome.test.js`: only the lifecycle tests need a stubbed `window`, a fake `navigator.audioSession`, and a fake audio graph. The runner isolates files from each other, but nothing isolates the tests inside one, so each fake global is installed against its saved property descriptor and restored afterwards rather than assigned once at module scope. `test/model.test.js` remains for pure domain and timing maths and stays browser-independent.
- The `playstate` event still fires when playback is requested, so the interface reports playing before any sound has been made. A run that never gets its audio now says so through `audioerror` once the threshold above passes; a positive "waiting for audio" indication for the interval before that is still unresolved.
- Recovery from a context that reports `running` while its render thread is dead is not attempted. Several open WebKit bugs describe that state, and no reliable detection exists short of watching `currentTime` for progress.
