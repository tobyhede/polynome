# Seed the example Presets into storage

The two example names and Configurations below, and every reference to the
storage key holding them, are superseded by
[ADR-0015](0015-refine-defaults-and-sliders.md) and then by
[ADR-0018](0018-give-each-cycle-a-timing-mode.md), which seeds one Cycle in
each Timing mode to take the examples to four and moves the key on to
`polynome-presets-v4`. Nothing below was rewritten for that count, so read
"two" as what a first run wrote when this decision was taken rather than what
it writes now. The seeding predicate and the ordinary-Preset behaviour this
decision establishes remain in force.

Polynome writes its two examples, `4/4` and `4/4 + 3/4`, into `localStorage` the first time it runs, as ordinary Presets. From that write on they are renameable, replaceable and deletable like any other, and "built-in" stops being a kind of Preset. Where Presets are kept does not change, and neither does anything ADR-0006 decided about reads treating storage as untrusted input; this decides what the store holds on a first run, not where the store is.

The two examples are `4/4 8ths` and `4/4 Triplets` since [PR #22](https://github.com/tobyhede/polynome/pull/22), and the key they are written under is `polynome-presets-v3`. Every consequence below reads the same with those two names substituted for `4/4` and `4/4 + 3/4` and `polynome-presets-v3` for `polynome-presets-v2`, with one exception that does not survive the substitution and is corrected where it stands. Which Presets are seeded was never what this decision settled — the seeding predicate is, and it is unchanged: `null` seeds, a written key never does. Why the key moved is corrected in [ADR-0006](0006-store-presets-in-browser-local-storage.md), where the retirement rule it contradicts is recorded.

This supersedes ADR-0003 where that decision recorded an immutable built-in catalogue, and the clause in ADR-0006 that has `createSavedPresets` reserve the built-in names. Both records are left as written, for the reason ADR-0009 gives when it leaves ADR-0004 and ADR-0006 standing: they record what was true when they were taken, and this is the record the change is read from. ADR-0003 does carry in-place supersession notes from ADR-0007 and ADR-0008, and that is a different case rather than a contrary precedent — those two replaced the step-level vocabulary running through nearly every consequence it records, so reading it uncorrected would misdescribe the whole record. Here it is one clause of one bullet in a record deciding something else.

"Built-in" was never one concept. It was five rules, and each existed only because those two Presets were not stored: a frozen list of two names standing as the source of truth; an identifier derived from the name rather than generated, because it had to survive a reload without being written anywhere; a reserved-name rule refusing the user a save under either name; a discard rule inside `createSavedPresets` dropping any stored entry that used one; and a second `apply-preset` payload shape, a name looked up against the frozen list, carried through `validPayload`, `leavesUnchanged` and `apply`. Seeding deletes all five. Nothing moves to the caller — the complexity stops existing, because after the first write there is no second kind of Preset to tell the first apart from.

The seeding predicate is the substance of the decision. Seeding an empty list would put the examples back the moment a user deleted the last one, which is the change undone. The distinction that matters is never written against written and now empty, and `localStorage` already draws it: `getItem` returns `null` for a key that has never been written and `"[]"` for one deliberately emptied. That reading is only trustworthy because nothing writes `polynome-presets-v2` speculatively — the read path reads, and the write path runs on a save and on a delete and nowhere else — so the key genuinely stays absent until the user acts. Polynome seeds on `null` and writes immediately. There is no second marker key, and so nothing new to guard under ADR-0006's rules for storage that refuses. There are no upgrading users either: the project is pre-release, so there is no migration to write and no marker needed to tell a returning user from an upgrading one.

The predicate lives in `configuration.js` behind `createStoredPresets(stored)`, which takes the raw stored value and decides. `null` seeds. A string is parsed and repaired through the existing `createSavedPresets` path. Malformed JSON yields an empty list rather than seeds, because malformed still means the key was written, and a value this version cannot parse is evidence that something wrote it. Put in `app.js`, the predicate would be reachable only from a browser test; here `test/configuration.test.js` reaches it directly, and `app.js` keeps the guarded read and the guarded write it already had.

## Consequences

- The single-file distribution opened over `file://` often cannot use storage at all, and there the examples are effectively undeletable. The write that would record the deletion is refused, so the key is still absent on the next load and seeding runs again. This follows from ADR-0006's existing refused-storage behaviour rather than being new — a browser that blocks storage keeps showing what it cannot persist — but the examples are the first thing that behaviour makes look broken rather than merely forgetful, so it is stated where someone will look for it. The two shapes a refusal takes now differ visibly, where before they agreed on showing nothing: a browser that forbids resolving the `localStorage` property still reports a refusal rather than an emptiness and opens on no Presets at all, while one whose `getItem` throws is indistinguishable from a key never written and opens on the examples, held in memory because the write that would record them is refused too.
- A user can delete every Preset and see an empty panel. That is intended, and not a state to defend against. A "restore examples" affordance is deliberately out of scope: it is an undo for a deliberate act, and it would first have to answer what restoring means once one example has been renamed and the other edited. That is a separate decision.
- Superseded by [PR #22](https://github.com/tobyhede/polynome/pull/22), which replaced both examples. It read: "`4/4` is exactly the default Configuration, so a user who deletes it reproduces it with a single Save on a fresh load. `4/4 + 3/4` has no such shortcut, and rebuilding it means adding the second rhythm layer and setting its meter by hand. The asymmetry is accepted, and it is the strongest argument the out-of-scope restore affordance has." Neither `4/4 8ths` nor `4/4 Triplets` is the default Configuration — both carry a subdivision the default does not — so neither has the shortcut and the asymmetry is gone. What replaces it is worse for the restore affordance rather than better: rebuilding either example is now one Subdivision edit rather than none, which is a smaller loss than rebuilding `4/4 + 3/4` was, but it is a loss both examples share and no deletion is free any more.
- On a genuinely fresh profile the `+ Save` chip is live at rest. The Configuration a first run opens on is the default, the two seeded Presets are not it, and `sameConfiguration` therefore answers that there is something to save before the listener has touched anything — where a first run previously read "No changes to save", because the seeded `4/4` was the Configuration on screen. Nothing is wrong with the offer; it is accurate, and taking it saves a third Preset that duplicates the default. It is recorded because it is a visible change to what an untouched Polynome looks like, and because the preset origin exists precisely to keep a reload from offering a save the user already made, which is the same question answered the other way.
- The decision is hard to reverse once there is a release. Today it costs nothing to undo, because the only storage holding a seeded example is a developer's own and AGENTS.md already treats that as disposable. After a release, going back to hardcoded examples means deciding what to do with two entries that may have been renamed, edited, or deleted, and no rule can tell an example a user kept from a Preset a user wrote — that nothing distinguishes them is the entire point. Reversal from there is a migration, which is what AGENTS.md rules out.
- ADR-0006's consequence about reads treating storage as untrusted says `createSavedPresets` "reserves the built-in names". That clause is now false. The function still discards malformed entries, repairs each Configuration, folds duplicate names case-insensitively and replaces any identifier that does not match the generated pattern; it reserves nothing, and `savePreset` no longer refuses a name with `preset-name-reserved`. That sentence stays as written there and this is where the correction is read from. `createStoredPresets` is a new door into the same repair, not a second repair.
- `apply-preset` carries a Configuration and nothing else. Applying by name is gone, and with it the `preset-not-found` outcome that only the name branch could produce. Every Preset now applies the snapshot it holds, which is what makes renaming an example unremarkable: the name is the Preset's identity and the Configuration is its content, and nothing rebuilds the second from the first.
- The save field offers an example's name back. It opens on the Preset the current Configuration came from, and while `4/4` was reserved that field had to open empty instead, because `savePreset` would have refused the name it was offering. The name is now offered like any other: the submit reads "Replace", and saving carries the edit onto the example rather than leaving a second Preset beside it. Starting a Preset of one's own from an example is still one act — renaming the field before saving — but it is the deliberate one rather than the only one available. `presetNameInUse` loses the same carve-out for the same reason, and answers on the stored list alone: a name an example holds is in use exactly as far as it is stored.
- Two members of `describeConfiguration`'s interface go with the five rules, and neither was reaching the interface. `choices.presetNames` is destructured by nothing in `app.js`, and `selectedPreset` could only ever match a built-in, because `describeConfiguration` is never handed the saved list and the panel uses `describePresets(...).selected` instead. Both were read only by `test/configuration.test.js`, which is what a seam kept alive by its own tests looks like. Removing the built-ins is what made that visible rather than what made it true.
- The tests worth naming are the ones the change is easy to regress into. `test/configuration.test.js` covers seeding on an absent value, not seeding on an empty-but-present one, and saving under a name that used to be reserved; an `e2e/` test deletes an example and reloads to prove it stays deleted. A predicate that reads the empty list instead of the absent key passes every other assertion in both suites.
- A `storage` event with a null key is another tab clearing storage wholesale, which leaves `polynome-presets-v2` absent, so the re-read seeds the examples again and writes them back into a tab that is already open. That is the intended answer rather than a case to guard: clearing this origin's storage returns it to a first run, and from inside the page there is nothing that distinguishes it from a browser opening Polynome for the first time. Inventing a difference would mean this one tab remembering that Presets once existed, which a tab opened a moment later could not agree with. It is not a deletion being undone — deleting Presets leaves `"[]"`, a written key, which is never seeded.
