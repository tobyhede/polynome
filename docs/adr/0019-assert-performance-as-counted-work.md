# Assert performance as counted work

Polynome will hold its performance with ratchets on **counted work** — nodes allocated, automation calls issued, events planned, selector calls per frame, artifact bytes — and will not assert elapsed time anywhere. This adds a third class of ratchet alongside the coverage thresholds and the TypeScript flags, and no new dependency.

The measurements this rests on are in [Performance optimisation and regression testing](../research/performance-optimisation-and-regression-testing.md).

## Why not time

The scheduler is not the cost centre and cannot be made into one. A whole tick — graph sync, planning, and committing every click — measures under 0.02 ms at the domain maximum of twelve 8/4 layers at subdivision four running at 300 BPM, against the 25 ms interval it has to fit inside. That is 0.07% of the budget in the worst case the domain permits.

Nothing useful can be asserted about a quantity that size on a shared runner. Measured on an *idle laptop*, the worst-case planning workload varied by 8.7% coefficient of variation with a 1.47× max/min spread; normalising against a control workload run in the same process did not help, coming out at 8.2% with a *wider* 1.69× spread, because a same-run control corrects for a sustained difference in machine speed and not for the GC pauses and preemption that the variance here actually is. A threshold on time can therefore only be set loose enough to catch nothing or tight enough to fail on a busy Tuesday, and between those, at 0.02 ms against a millisecond noise floor, there is no band.

Counted work has none of that problem. The same workload returned exactly one distinct event count over 200 identical runs. A count is a property of the code rather than of the machine, it is identical on every runner, and it is the thing that actually changes when a regression lands.

`performance.now()` settles the question from the other side: it is quantised to 100 µs outside a cross-origin-isolated context, which is coarser than a whole scheduler tick. Polynome is served without COOP/COEP. An in-page timing of this application would be measuring the clock.

## Consequences

- Four files hold the ratchets. `test/artifact-size.test.ts`, `test/audio-work.test.ts` and `test/transport-work.test.ts` are `node --test` and need no browser. `e2e/performance.spec.ts` is Chromium, and only because the DOM costs it counts have nowhere else to live — building a DOM in Node to count them would be measuring the fake.
- `test/audio-work.test.ts` drives the real `MetronomeEngine` through the `options.createContext` seam that ADR-0005 already established for the audio-lifecycle tests, with a counting double and a stubbed `window.setInterval`. The code under measurement is the shipped scheduler, not a restatement of it. The seam now carries a second purpose and must not narrow.
- Node allocation is asserted as an **equality** against clicks sounded, not as a budget. Two nodes per click is the Web Audio specification's own design — §1.1.6 describes source nodes created per note and never removed — so the failure worth catching is anything that starts allocating per *tick*, which an equality catches and a rate does not.
- The per-tick graph sync is ratcheted at what it currently costs, which is waste: `#schedule()` calls `#syncNodes()` on every tick, so the engine issues 120 `setTargetAtTime` calls per second at the default Configuration against the six a click needs — 95% of all automation traffic restating values already in force, and 58% at twelve layers. Recording it is not endorsing it. Removing the per-tick sync is the highest-value optimisation identified, it changes the engine's contract about how far behind `#state` the graph may be, and it needs its own decision record. Lowering these two numbers is what will record that it happened.
- Planned-event counts are equalities, and the invariants beside them say which behaviour moved when one changes: every absolute step emitted exactly once, `audioTime` non-decreasing within and across ticks, every event inside `[currentTime − 4 ms, horizon)`, and nothing emitted for an `off` position. The Peak envelope's amount is stated in the test rather than defaulted, because a moving tempo covers a different number of steps in the same wall interval and `ENVELOPE_DEFAULT_AMOUNT` changing would move the counts for a reason that has nothing to do with the transport.
- `e2e/performance.spec.ts` asserts the read-before-write ordering in `layoutSteps` as a **correctness property**, not a threshold. Interleaving costs one synchronous reflow per rhythm instead of one for the pass, on every render including every step click, and the cost grows with the number of layers on screen. The assertion is scoped between the first and last `--beats-per-row` write, because a step click renders through Preact first and reconciliation writes inline styles of its own well before the pass begins; treating those as the boundary reports the measure loop as a violation of an ordering it satisfies.
- The playhead's per-frame selector cost is ratcheted at its structural maximum, `3C + 2R` selector calls and `C + R` `CSS.escape` calls, plus one `querySelectorAll(".step")` per rhythm on a frame where an onset moves the highlight — 6 and 2 at one layer, 39 and 13 at twelve. Caching those lookups is a candidate optimisation, and this is the measurement it was waiting for; what a selector call costs in a real engine is still unmeasured, so the ratchet records the count without arguing that it should fall.
- The long-task assertion measures **steady-state** playback, with the observer installed after the run settles. Creating the `AudioContext` is a genuine long task of roughly 130 ms, it happens once, and it cannot happen before the gesture that permits it; including it would assert that starting audio is free, which is not a property anything can hold. This is the only assertion in the suite with any dependence on runner speed, and it is a boolean against a threshold three thousand times the measured cost of a tick.
- Artifact byte budgets are taken against `main` and re-taken there whenever one is raised. Measured on a feature branch instead they came out 4 KB lower on the script and 3 KB higher on the stylesheet, and a budget carrying one branch's shape reads as a regression the moment another merges. The build is byte-reproducible, which is what makes a budget an assertion rather than a sample, and a test asserts that too.
- Compressed budgets name their compressor. Node's `zlib.gzipSync` at level 9 and the system `gzip -9` disagree by tens of bytes on identical input, so raw bytes carry the budget wherever only one figure is stated. For the single-file distribution raw bytes are also the honest number: roughly 65 KB of it is base64-encoded woff2, ~~which compresses to nothing~~ and would mask real script growth behind a flattering total.

The decision is unaffected and the conclusion this bullet draws is the right one, but it holds for the opposite reason: the faces are an incompressible floor that dilutes a gzipped total, rather than a term that disappears from it, and script growth measured against so diluted a figure reads smaller than it is. `test/artifact-size.test.ts` now asserts this rather than describing it, so the claim cannot drift again without a test failing.
- No dependency is added. `size-limit` was rejected because its byte half is twenty lines of `node:fs` and its time half is a timing measurement on a shared runner. Lighthouse CI was rejected because its metrics are load-time metrics for content pages and its own documentation says free CI environments are too volatile for it. `tinybench` and `mitata` were rejected narrowly — both are small and dependency-free and both are the right tool for an interactive investigation — because what they produce is a distribution, and no distribution should gate CI. Use one in a scratch file; do not commit it.
- Chrome DevTools' WebAudio **Render Capacity** is the most useful audio-performance number in any browser and is unreachable from page script and from CDP. There is no automated substitute, and audio-thread headroom stays a manual check alongside the physical-output checks ADR-0004 already left there.
